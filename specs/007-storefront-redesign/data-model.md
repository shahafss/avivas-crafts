# Data model: Storefront redesign (007)

What this feature adds or changes. The whole model's source of truth stays the Drizzle schema in
`src/server/db/schema/`. Two database changes: social links (three columns, §1) and several
categories per piece with the home-row category (a join table, one column added, one removed,
§5); the home photos and texts are code, not data.

## 1. `shop_settings`: social links (new columns)

Table `shop_settings` (single row, `id = 1`, `src/server/db/schema/commerce.ts`) gains:

| Column | Type | Null | Default | Rule |
|---|---|---|---|---|
| `social_facebook_url` | `text` | yes | `NULL` | `NULL`, or a normalised `https://` address on `facebook.com` or a subdomain of it |
| `social_instagram_url` | `text` | yes | `NULL` | same, on `instagram.com` |
| `social_tiktok_url` | `text` | yes | `NULL` | same, on `tiktok.com` |

Drizzle fields: `socialFacebookUrl`, `socialInstagramUrl`, `socialTiktokUrl`.

**Database checks** (second line of defence; the full rules are in the shared Zod schema, see
[contracts/social-links.md](contracts/social-links.md)):

- `shop_settings_social_facebook_url`: `social_facebook_url IS NULL OR (social_facebook_url LIKE 'https://%' AND char_length(social_facebook_url) <= 300)`
- the same for `social_instagram_url` and `social_tiktok_url`.

The platform-domain rule is not repeated in SQL (hard to express safely there); every write goes
through `updateSettings`, which applies the Zod schema first.

**Migration**: `src/server/db/migrations/0005_social_links.sql`, generated with
`pnpm db:generate` after the schema edit. Adds the three nullable columns and the three checks.
No data migration: existing shops start with no social links. Reversible by dropping the columns.

**Purpose and retention** (constitution VII): these are the shop's own public page addresses, not
personal data of customers or visitors. Kept while the shop exists; cleared by Aviva by emptying
the field. Not shown in exports of customer data.

**Who writes**: an admin through `updateSettings` (Server Action guarded by `requireAdmin`), which
writes one `settings.updated` activity row with the count of changed fields (existing behaviour;
the addresses themselves are not written to the log).

**Who reads**: `getSettings()` (already returns the whole row) → the locale layout → `Footer`
(public, every page) and the admin Settings page.

**Types**: `Settings` (`typeof shopSettings.$inferSelect`) gains the three fields automatically.
`SettingsInput` (Zod) gains three optional fields; `SettingsData` (the client props of
`SettingsManager`) gains three `string | null` fields.

## 2. Home photos (code, not database)

Defined in `src/lib/home-photos/config.ts` and `src/lib/home-photos/manifest.json`
([contracts/home-photos.md](contracts/home-photos.md)).

`HomePhotoConfig` (one per photo: `hero`, `bannerChild`, `bannerShelf`):

| Field | Meaning |
|---|---|
| `id` | `'hero' \| 'bannerChild' \| 'bannerShelf'` |
| `source` | file in `assets/home-photos/` |
| `focusX` | 0–1, the main subject's horizontal position, used to cut the phone crop |
| `wideObjectPosition` | literal Tailwind classes for the wide crop (e.g. `'sm:object-[50%_50%]'`) |
| `altKey` | translation key of the alt text (`shop.home.<id>.alt`) |

`HomePhotoManifest` (generated by `pnpm photos:home`; never edited by hand):

```text
{ [id]: {
    phone: [{ file, width, height, bytes }]  // 400×600 and 565×848, WebP
    wide:  [{ file, width, height, bytes }]  // 800, 1200, 1600, 2000 wide, WebP
} }
```

`file` is the name inside `public/site-photos/`, with a content fingerprint.

## 4. Unchanged

Images (stored 4:5 variants stay), orders, content pages, consent and
statistics are unchanged (apart from counting `/shop`). "You may also like" is a read query over
`product.state`, `product_category`, `product.published_at` and `product.created_at`.

## 5. Several categories per piece and the home-row category

Owner answers 2026-11-16 (spec decision 12, FR-031–FR-034, FR-037): no separate collections; a
piece can be in several categories, and a setting names the category the home row shows
("Featured" at release). Contract: [contracts/home-row.md](contracts/home-row.md).

### New table `product_category` (`src/server/db/schema/catalog.ts`)

| Column | Type | Null | Rule |
|---|---|---|---|
| `product_id` | `uuid` | no | `REFERENCES product(id) ON DELETE CASCADE` |
| `category_id` | `uuid` | no | `REFERENCES category(id) ON DELETE RESTRICT` (as `product.category_id` today: a category with pieces cannot be deleted) |
| `created_at` | `timestamptz` | no | shared helper |

Primary key `(product_id, category_id)`; index `product_category_category_idx` on `category_id`.

### Removed: `product.category_id`

The column and its index `product_category_idx` are dropped after their values are copied into
`product_category` (below). Drizzle: `product.categoryId` disappears; types that carried it
(`ProductInput`, `PublishFacts`, admin and public product shapes) carry `categoryIds: string[]`
instead (public product detail: `categories` and `mainCategory`, FR-037).

### `shop_settings.home_category_id` (new column)

`uuid`, nullable, `REFERENCES category(id) ON DELETE SET NULL` (only an empty category can be
deleted, so in practice this clears an empty row). `null` = no home row. Drizzle field
`homeCategoryId`; `SettingsInput` gains `homeCategoryId: z.uuid().nullable().optional()`.

### Migration `0004_product_categories.sql` (with the release step)

Generated with `pnpm db:generate --name product_categories` after the schema edit, then edited
by hand (as `0001` was) so the data steps run between creating the table and dropping the
column, all in the migration's transaction:

1. Create `product_category`, its keys and index; add `shop_settings.home_category_id`.
2. `INSERT INTO product_category (product_id, category_id) SELECT id, category_id FROM product
   WHERE category_id IS NOT NULL` (every piece keeps its current category).
3. Create the category `featured` ("מומלצות" / "Featured") with `sort_order` =
   `coalesce(max(sort_order), -1) + 1` (0 on an empty table), unless a category with slug
   `featured` exists (then reuse it). "Last" therefore holds for the release on existing data; on
   a fresh dev database the seed's sample categories come after it, which only affects local
   ordering.
4. `INSERT INTO product_category SELECT p.id, <featured id> FROM product p ON CONFLICT DO NOTHING`
   (every existing piece, any state; only published ones are shown).
5. `UPDATE shop_settings SET home_category_id = <featured id> WHERE home_category_id IS NULL`.
6. Drop `product.category_id` and its index.

The drizzle snapshot matches the final schema, so later `db:generate` runs stay clean.
Reversible only with a hand-written down step (re-add the column and copy the main category back);
the backups from feature 006 cover a failed release.

### Seed

Test resets (`tests/e2e/fixtures.ts` `resetDb()`, `tests/setup/pglite.ts` `reset()`) empty every
table, including `category`, and then seed again, so the seed cannot rely on the migration's
`featured` row:

- `seedInTx` creates or reuses `featured` (by slug, `ON CONFLICT (slug) DO NOTHING`, Hebrew and
  English names, `sort_order` = `coalesce(max(sort_order), -1) + 1`) **only** when it inserts a new
  settings row or when `samples` is true, and after the sample categories (so it is last there
  too). A new settings row gets `home_category_id` = its id. An existing settings row is never
  changed (`null` there means Aviva chose "no row"), and a production deploy (settings row exists,
  no samples) never re-creates "Featured" after Aviva deleted it.
- With `samples` (dev and tests): after `seedSampleProducts`, each sample product is linked to its
  sample category and to `featured`, idempotently (`ON CONFLICT DO NOTHING`).

### Who writes / reads

- Writes: admins only, through the existing product save (`categoryIds`) and `updateSettings`
  (`homeCategoryId`), behind `requireAdmin`, logged by the existing `product.updated` /
  `settings.updated` activity rows.
- Reads: category page, "All pieces" chips, sitemap, `getHomeRow` (published pieces only), product
  page (`categories`, `mainCategory`), admin lists and counts.
- Not personal data (constitution VII).

## 6. Header categories and category name length (Phase D gate, FR-039, FR-040, research D20)

### `shop_settings` (two new columns)

| Column | Type | Rule |
|---|---|---|
| `header_category_1_id` | `uuid`, nullable | FK `category.id`, `on delete set null`; null at release |
| `header_category_2_id` | `uuid`, nullable | FK `category.id`, `on delete set null`; null at release |

Migration `0006_header_categories.sql` (`pnpm db:generate --name header_categories`): adds the two
columns and their foreign keys. No data step. The seed leaves them null.

Validation (`src/lib/validation/settings.ts`): `headerCategory1Id`, `headerCategory2Id`:
`z.uuid().nullable().optional()`; the save checks each id exists, else the field error
`admin.settings.errors.header_category_not_found` (new message, he/en, worded like
`home_category_not_found`). Activity: the existing `settings.updated` row.

`getSettings()` returns the two ids as `headerCategory1Id` and `headerCategory2Id` (null when not
set).

Public read (no new query): the locale layout already loads `getSettings()` and
`listCategoriesWithProducts()`; a pure function `pickHeaderCategories(settings, categories)` in
`src/server/catalog/header-categories.ts` takes [header 1, header 2, home-row category] from the
settings, drops nulls, drops ids not in `categories` (no published piece), drops repeats (first
wins), and returns those `PublicCategory` rows in that order (at most 3). The header renders each
name for the page language with the existing Hebrew fallback (as the menu does today).

### `category` names

No schema change and no data step (no existing category is longer than 12; owner answer).
`src/lib/validation/category.ts`: `nameHe` and the optional `nameEn` `max(12)`, used by create and
update alike. `src/server/catalog/categories.ts` maps a `too_big` issue on either name to the field
error `admin.categories.errors.nameTooLong` (every such issue, both fields at once; the optional
English name is trimmed before its length check); other issues keep `admin.categories.errors.invalid`
(its text now says 12, not 80). In the header each category name sits in a span capped at 95 px
with an ellipsis, which only an unusual name of wide letters reaches (research D20).
