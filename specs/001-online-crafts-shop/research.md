# Research: Aviva's Crafts Online Shop

**Feature**: `001-online-crafts-shop` | **Date**: 2026-11-07 | **Plan**: [plan.md](./plan.md)

Each section records a decision, why it was made, and what else was considered. Prices were
checked on 2026-11-07 and are in USD unless marked ₪; the plan converts at ₪3.7 per USD
(a deliberately pessimistic rate).

---

## R1. Application framework and language

**Decision**: One TypeScript application built with **Next.js 16 (App Router, React 19)** on
**Node.js 24 LTS**, package manager **pnpm 12.6.0** (run through Corepack, pinned in
`packageManager`; user decision 2026-11-08), all versions pinned exactly. pnpm 12 reads its
settings from `pnpm-workspace.yaml` (`saveExact`, `engineStrict`, `allowBuilds` for packages with
install scripts such as sharp and esbuild) and keeps only auth/registry keys from `.npmrc`.

**Rationale**:
- One codebase serves the storefront, the admin area, server-side logic, the payment webhook and
  background jobs. No separate API service to deploy or secure.
- Server Components render most pages on the server: little JavaScript reaches phones (SC-005),
  pages are indexable, and share previews (FR-049) come from `generateMetadata`.
- Server Actions give form posts with built-in Origin checking (CSRF defence) and work without
  client-side state libraries.
- Mature Hebrew/RTL i18n with per-locale URLs is available (R5).
- It is the stack the implementer agent knows best, which lowers implementation risk.

**Alternatives considered**:
- *SvelteKit / Astro*: smaller bundles, but weaker i18n routing support and less familiar to the
  implementer; no decisive benefit at this scale.
- *Separate SPA + REST API*: two deployables, CORS, token handling. More attack surface, more
  cost, no benefit.
- *Hosted shop builders (Shopify, Wix)*: monthly fees above budget at useful tiers, limited
  control of the security baseline (passkey admin 2FA, CSP), Hebrew checkout quality varies,
  and the project explicitly wants its own shop.

## R2. Hosting

**Decision**: **Render**, Frankfurt region, Hobby workspace:
- Web Service *Starter* (512 MB, 0.5 CPU, always on): $7/month.
- Render PostgreSQL *Basic-256mb* (PostgreSQL 17): $6/month + storage $0.30/GB/month.
- One Render *Cron Job* for the nightly encrypted backup: billed per minute, $1/month minimum.
- **Cloudflare** (free plan) for DNS, and optionally as a caching proxy in front of Render for
  `/_next/static/*` assets (Render's Hobby workspace includes 5 GB/month bandwidth, overage
  $0.15/GB; product images do not count because they are served from R2, see R8).

**Rationale**:
- Managed TLS, git-push deploys, a secret store (environment variables / secret files), private
  networking between the app and the database, and point-in-time recovery for paid databases
  (3-day window on Hobby). No servers to patch.
- Frankfurt keeps personal data in the EU, which Israel recognises as an adequate destination
  for transfers under the Privacy Protection (Transfer of Data to Databases Abroad) Regulations
  and which is natively GDPR-compatible. Round-trip from Israel ≈ 60 ms.
- A long-running Node process (not serverless) suits `sharp` image processing and an
  in-process job loop (R12) and has no cold starts.
- Total infrastructure ≈ $14.5/month (see plan › Cost).

**Alternatives considered**:
- *Vercel*: Hobby plan forbids commercial use; Pro is $20/month per member, and a database is
  still extra. Over the budget's comfort zone.
- *Cloudflare Workers + D1*: cheapest, but no `sharp` (native image library); in-Worker WASM
  image decoding of 12 MP phone photos sits at the 128 MB memory limit. Too risky for FR-004.
- *Fly.io*: similar price, but SQLite-on-volume or self-run Postgres means more operations work.
- *Plain VPS (e.g., Hetzner, €5/month)*: cheaper, but OS patching, TLS, backups and monitoring
  become the family's job. Violates "low-maintenance hosting" in principle V.
- *Neon / Supabase free database*: saves $6/month, but adds a vendor, a public database
  endpoint, and short (hours) restore windows on free plans; Supabase Pro ($25) is over budget.

## R3. Database access

**Decision**: **PostgreSQL 17** via **Drizzle ORM** with the **postgres.js** driver; schema in
TypeScript, migrations generated by **drizzle-kit** and committed. Integration tests run on
**PGlite** (in-process Postgres) so no Docker is needed for unit/integration tests; E2E tests
use a real local Postgres.

**Rationale**: Parameterised queries only (no raw query building, principle IV); typed schema;
light runtime (no engine binary, unlike Prisma); SQL-like API keeps row locks
(`SELECT … FOR UPDATE … SKIP LOCKED`) and lease updates straightforward, which the payment idempotency logic
needs.

**Alternatives considered**: *Prisma* (heavier, separate engine, awkward row locking);
*Kysely* (good, but Drizzle also handles migrations); *SQLite* (simpler, but Render's managed
backups/PITR are for Postgres, and SQLite on a disk needs self-managed backups).

## R4. Payment provider (online payment)

**Decision**: **PayPlus** hosted payment page, behind a small `PaymentProvider` interface
(`src/server/payments/provider.ts`) so another Israeli provider can be swapped in by writing
one adapter file. A `fake` adapter is used in tests and local development.

Flow (details in [contracts/payment-provider.md](./contracts/payment-provider.md)):
1. Checkout creates a *pending checkout* record and calls PayPlus *Generate Payment Link* with
   the amount, currency, the checkout's id as reference, and success/failure/callback URLs.
2. The visitor is redirected to PayPlus and enters card or Bit/Apple Pay/Google Pay there. The
   shop never sees card data.
3. PayPlus calls the callback URL. The shop verifies the `hash` header (HMAC-SHA256 with the API
   secret, Base64) **and then** queries PayPlus's *IPN* endpoint server-to-server by the payment
   page request id, and checks status, amount and currency against the pending checkout. Only
   then is the order confirmed. The browser return URL triggers the same server-side IPN check
   (covers the "callback has not arrived yet" race) and never marks anything paid by itself.
4. Confirmation runs inside one database transaction with a row lock and a unique constraint
   on the provider transaction id, so a repeated callback is a no-op (FR-019). A paid status
   with a *different* transaction id for an already-confirmed checkout, or for a checkout the
   visitor switched to offline payment, never creates an order; it alerts the owner (a second payment to refund; after a switch, the alert names the
   offline order and the owner decides whether to keep the online payment for it or refund it).
5. A five-minute **recovery sweep** queries the status of checkouts still awaiting the provider or
   marked failed (lost callbacks; a declined page may be paid on a second try), expiry asks the
   provider one last time before deleting a checkout, and retry/switch disables the previous payment page (*Disable Payment
   Link*), so an old page cannot be paid later. A failed disable call is logged and never blocks
   retry/switch; a late payment of an old page is then caught by the `second_payment` /
   `payment-attention` / mismatch alerts (plan › Risks).
6. **Open point to verify in the PayPlus sandbox before launch**: the exact HMAC input (raw body
   vs. re-serialised JSON), the IPN response fields, whether *Disable Payment Link* exists and stops
   an open page from being paid, and whether a page can be given a 24-hour expiry. The launch
   checklist includes these checks.

The status query authenticates the shop to PayPlus with its API key over TLS; it is what
confirms a payment on the browser-return and recovery-sweep paths, where no signed callback is
involved. **Decision (user, 2026-11-07)**: this authenticated server-to-server status query is
accepted as meeting the constitution's "signature-verified confirmation" rule, alongside the
signed callback.

**Provider (user, 2026-11-07)**: PayPlus confirmed. Its pricing is not published; the user will
get a quote. The ₪100/month target leaves about ₪37/month for its monthly fee.

**Rationale**:
- Public REST documentation, a sandbox environment with test card numbers, signed callbacks
  plus an IPN status endpoint (two independent server-side verifications), hosted page with
  Bit, Apple Pay and Google Pay as "alternative methods", multi-currency (ILS and USD), and
  an optional invoicing module (Invoice+) the owner could use later for tax receipts.
- The second check (IPN query) makes verification robust even if the callback's HMAC input
  format is ambiguous (PayPlus's sample hashes a re-serialised JSON body).

**Commercial terms are not public.** PayPlus and Cardcom quote monthly fees and per-transaction
rates on request; Grow (Meshulam) via morning lists plans from about ₪29/month plus a
subscription, with 1.2–1.6% per transaction. The monthly terminal fee counts toward the
₪100/month target (SC-011 only excludes per-transaction fees), so **the provider must be
confirmed by the user after getting quotes** (question raised at the gate). The adapter design
keeps that decision cheap to change.

**Alternatives considered**:
- *Cardcom*: very common in Israel, hosted "Low Profile" page with Bit, server-side
  `GetLpResult` verification, built-in receipts. Equally valid; unsigned webhook (verification
  relies on the server-side query only). Good second choice.
- *Grow (Meshulam)*: popular with small businesses, public plan pricing, Bit support. API
  verification via server-side transaction query; documentation less complete.
- *Tranzila, Hyp (YaadPay)*: established; older APIs, less convenient sandbox.
- *Stripe / PayPal*: Stripe does not onboard Israeli merchants; PayPal does not support Israeli
  cards with Bit and has poor local fit.

## R5. Internationalisation and RTL

**Decision**: **next-intl** with locale-prefixed routes `/he/...` and `/en/...`
(`localePrefix: 'always'`), Hebrew default. `/` redirects to the remembered locale (cookie
`NEXT_LOCALE`) or Hebrew. `<html lang dir>` set per locale. All UI strings come from
`src/i18n/messages/he.json` and `en.json`; a unit test fails if the key sets differ or a
component contains hard-coded display text (lint rule `no-literal-string` scoped to
`src/app` and `src/components`). Layout uses CSS logical properties (Tailwind 4 `ms-*`, `pe-*`,
`start-*`) so English renders true LTR, not mirrored. The admin area is Hebrew-only (FR-044) but
still takes strings from `he.json` (constitution I).

**Rationale**: FR-041–FR-045; shareable per-language URLs (FR-043) come for free; the locale
cookie is set only when the visitor chooses a language (a user-requested preference, strictly
necessary).

**Alternatives considered**: *Cookie-only locale without URL prefix* (fails FR-043);
*react-i18next* (no routing integration).

## R6. Admin authentication (Google + passkey)

**Decision**: Custom, small auth module (no auth framework):
- **Step 1 — Google**: OpenID Connect authorisation-code flow with PKCE, `state` and `nonce`,
  using **openid-client** (certified OIDC relying-party library). Accept only if
  `email_verified` is true and the email is on the approved list; on first success the admin
  row is bound to Google's stable `sub`, and later sign-ins match by `sub`. Result: a
  *pending-2FA* session (5-minute lifetime) that can reach nothing but the passkey step.
- **Step 2 — Passkey**: WebAuthn via **@simplewebauthn/server** / **@simplewebauthn/browser**
  with `userVerification: 'required'` and `residentKey: 'preferred'`. User verification is
  satisfied by the device's screen-lock PIN/passcode; the shop never asks for biometrics, so
  fingerprint/Face ID is never required (FR-031). Allowed credentials are limited to the
  admin's own registered passkeys. Counter and backup flags stored.
- **First passkey**: requires a one-time **setup link** `/admin/setup#t=<token>` (the token sits in
  the URL fragment, so it never reaches the server's request logs; the page posts it; 32-byte random token, stored hashed,
  24-hour expiry) created by the maintainer CLI (first admin) or by an existing admin when
  adding a new one. This stops someone who has stolen an approved Google account before
  enrolment from registering their own passkey.
- **Recovery codes**: 10 codes of 12 characters (Crockford Base32, 60 bits), shown once,
  stored as salted `scrypt` hashes (Node built-in, no dependency). Google sign-in + one code
  → register a new passkey; the code is consumed and all admins are emailed. Because Google +
  code are both phishable, the new passkey does not grant full access by itself:
  **Hardened recovery** (user decisions 2026-11-07 and 2026-11-08): a passkey registered through a
  recovery code is always created with `status = pending_approval` — it cannot be used to sign in,
  the recovering admin gets no `full` session, every admin and notification address is emailed,
  and another admin must approve it on the security screen (unapproved passkeys are deleted after
  7 days). Recovery therefore needs a second admin with an active passkey: when none exists,
  `/api/auth/recovery` refuses **before** checking the code (no code is consumed), the recovery page
  tells the admin to contact the maintainer, and the maintainer restores access with
  `pnpm admin:reset` (server-side CLI: removes that admin's passkeys, codes and sessions and prints a
  new one-time setup link). The shop always has two admins — the maintainer and Aviva — both set up
  before launch (launch checklist), so this refusal is a safety net, not a normal path. The earlier
  24-hour restricted mode for a sole admin was dropped (2026-11-08). First-time setup links are
  unchanged (one-time, delivered by the maintainer or an admin).
- **Re-check before security changes** (user decision 2026-11-08, ASVS 5.0 V7.5.1/V7.5.2): adding or
  removing an admin, creating a setup link, adding, removing, approving or rejecting a passkey,
  regenerating recovery codes and clearing another admin's sign-in block require a passkey assertion (UV required) within the last 5 minutes on
  the current session (`admin_session.reauth_at`; the sign-in assertion itself counts). Otherwise
  the action answers `reauth_required` and the screen asks for the passkey (`/api/auth/reauth/*`)
  and retries. Failed re-checks count toward the passkey throttle. Revoking a session and "sign out
  everywhere" are exempt (user decision 2026-11-08): they only reduce access, and an admin whose
  re-checks are blocked must still be able to end sessions.
- **Sessions**: opaque 32-byte random token in cookie `__Host-ac_admin` (Secure, HttpOnly,
  SameSite=Strict, Path=/); only its SHA-256 hash is stored. Idle timeout 30 minutes,
  absolute lifetime 12 hours (ASVS 5.0 V7 L2), session id rotated after each step, "sign out of
  all devices" deletes every session of the admin. Admin links opened from another site (e.g. the order
  link in a notification email) arrive without the Strict cookie: the proxy answers such cross-site
  top-level GETs of admin pages with a minimal same-site re-navigation page (the Google callback's
  mechanism; no session is read), and a signed-out visit carries a validated same-origin `next` path
  through sign-in (`oauth_flow.next_path` → pending session → passkey-verify redirect).
- **Throttling**: 5 failed passkey attempts per admin in 15 minutes → 15-minute block and an
  email to all admins. A Google sign-in whose passkey step is never completed (session expires or
  is replaced) also counts as a failure and triggers a throttled alert — this is the signal for a
  stolen Google account, whose holder has no passkey and so never reaches the verify endpoint; 10 Google sign-in attempts per IP-hash per 15 minutes; unapproved-account
  sign-ins are blocked and reported by email (at most one email per 15 minutes per kind).
- **Synced passkeys (accepted residual risk, user decision 2026-11-08)**: the owner's Android phone
  keeps passkeys in Google Password Manager, which syncs them under the same Google account that is
  the first factor. Synced passkeys are end-to-end encrypted; restoring them on a new device needs an
  old device's screen lock or the Password Manager PIN, so a stolen Google password alone does not
  give the passkey. The factors are therefore not fully independent; this is accepted and recorded in
  constitution IV 1.3.0 (synced passkeys allowed) and the threat model. `admin_passkey.backed_up`
  shows which passkeys are synced.

**Rationale**: Meets constitution IV (two factors, one phishing-resistant, no passwords,
rate-limited, allowlist, expiring/revocable sessions) and FR-031–FR-035 exactly, with two
well-maintained single-purpose libraries.

**Alternatives considered**: *Auth.js (NextAuth)*: large surface, passkey support marked
experimental, two-step Google-then-passkey flow is awkward to express. *Better Auth*: capable,
but brings its own schema and many features unused here. *Lucia*: deprecated as a library
(now a guide; the session design above follows it).

## R7. Image processing

**Decision**: **sharp** (libvips). On upload the server: checks the size (≤ 20 MB) and pixel
count (≤ 51,000,000 pixels, `limitInputPixels: 51_000_000`, so 50 MP phone photos — e.g. 8160×6144 ≈
50.1 MP — are accepted; a 50 MP decode needs ~150–200 MB), detects the real format from the content (JPEG, PNG, WebP
accepted; anything else — including files renamed to `.jpg` — rejected with a clear Hebrew
message), applies EXIF orientation (`rotate()`), and re-encodes to **WebP** at widths 400, 800
and 1600 px. sharp drops all metadata (EXIF, GPS, XMP, ICC except sRGB conversion) unless
explicitly asked to keep it. The original upload is processed in memory and **never stored**,
so GPS data never reaches storage. `sharp.concurrency(1)` and a one-at-a-time upload queue keep
memory within the 512 MB instance.

HEIC/HEIF: the owner uses an Android phone, which can save photos as HEIC/HEIF (Samsung's
"high efficiency pictures" setting), and browsers on Android upload the file as-is. sharp's
prebuilt binaries cannot decode HEVC-based HEIC (patents), so HEIC/HEIF files — detected by their
`ftyp` brand (`heic`, `heix`, `heif`, `mif1`, `msf1`), not by name — are decoded with
**heic-decode** (libheif compiled to WebAssembly, so a malformed file stays inside the WASM
sandbox), which returns raw pixels only (no metadata, transformations applied); the pixels then go
through the same sharp pipeline. The 20 MB limit and the pixel limits (51 MP; for HEIC/HEIF the lower
`HEIC_MAX_PIXELS`, see the whole-app gate below) are checked before decoding (dimensions from the
HEIF header). The owner guide also explains how to switch the camera to JPEG if uploads
are slow.

**Rationale**: FR-003, FR-004, constitution IV uploads rule, SC-009 (test asserts no EXIF/GPS in
every stored variant).

**Alternatives considered**: *Cloudflare Images* ($5/month minimum plus usage; adds a vendor);
*client-side resizing only* (cannot be trusted; server must re-encode anyway); *Next.js image
optimiser* (CPU on the small instance at request time; we pre-generate variants instead and
serve them with `unoptimized` images and a hand-written `srcset`).

**Measured (T025, 2026-11-08, early warning)**: `scripts/measure-image-memory.ts` in
`node:24-bookworm-slim` (`linux/arm64`, `--memory=512m`, dependencies installed in the container),
peak RSS of the process that runs the pipeline, one fresh process per case:

| Input | Peak RSS | Time |
|---|---|---|
| JPEG 8160x6144 (50.1 MP) | 143 MB | 0.8 s |
| HEIC 640x480 | 133 MB | 0.2 s |
| HEIC 8160x6144 (50.1 MP, `large.heic`) | **544 MB** (over the 300 MB threshold) | 3.7 s |

The HEIC peak is the `heic-decode` WebAssembly decode itself (about 490 MB above the idle process,
reached before sharp touches the pixels; the sharp stage after it adds nothing to the peak). It
runs inside the 512 MB container without being killed here, but leaves no room for the rest of the
app, so this is reported to the coordinator; the gate is the whole-app measurement in T052.

**Whole-app gate (T052, 2026-11-08)**: `scripts/measure-app-memory.ts` builds the app and runs
`next start` (`APP_ENV=development`, `STORAGE_DRIVER=fs`, Docker dev database through
`host.docker.internal:5433`) in `node:24-bookworm-slim` on `linux/arm64` with
`--memory=512m --memory-swap=512m` (no swap, like Render), dependencies installed in the container.
It creates a temporary admin with a `full` session and uploads through `POST /api/admin/images`, in
one fresh container per HEIC candidate: idle, the 8160x6144 JPEG, the HEIC, then the 50 MP
`large.heic`. "Peak" is the container's cgroup `memory.peak` (it includes page cache, so it is a
conservative figure; the sampled anonymous memory is shown for comparison).

| Step (16 MP HEIC candidate, 4608x3456 = 15.9 MP, 6.1 MB file with sensor-like grain) | Peak (`memory.peak`) | Anonymous memory peak in the step | Result |
|---|---|---|---|
| `next start`, idle (node RSS 175-177 MB) | 126-127 MB | 90 MB | |
| + JPEG 8160x6144 (50.1 MP) | 232-247 MB | 196-212 MB | 201, about 1.0 s |
| + HEIC 4608x3456 (15.9 MP) | **421-435 MB** (3 runs: 435, 421, 432) | 365-383 MB | 201, about 2.4 s |
| + HEIC 8160x6144 (`large.heic`) | unchanged | - | 400 `too_many_pixels` in 15 ms, not decoded |

The first measurement used a smooth-gradient fixture of 76 KB, which understates the work of a real
photo (a 3-6 MB HEVC stream and several copies of the upload alive during the decode); the numbers
above are from the textured fixtures `make-heic.sh` now generates (the route also drops the raw
body once the form is parsed). The textured 16 MP file costs about 7 MB more than the gradient one.

No OOM kill (`oom_kill` 0, `State.OOMKilled` false), the app still answered `/api/health`
afterwards, and the highest peak (435 MB) is under the 460 MB threshold, so the 16 MP candidate passes
and the 12 MP fallback (4000x3000, not needed) was not run. **Decision: `HEIC_MAX_PIXELS` =
16,000,000** in `src/server/images/process.ts` (checked on the HEIC header before decoding, again
on the decoded size; JPEG, PNG and WebP keep 51,000,000). The HEIC decode is the largest consumer by
far (about 11 bytes per pixel in the WebAssembly heap, which grows without shrinking until the
worker is terminated); a 16 MP photo took the app from about 240 MB to 435 MB. The margin to 460 MB is
small, so any change to the limit, the worker or the dependencies re-runs the gate. A few 16 MP
sensors report slightly more than 16,000,000 pixels (e.g. 4640x3472 = 16.1 MP); such photos get the
Hebrew message asking for the normal resolution or a JPEG (`admin.images.errors.too_many_pixels_heic`).
The same measurement is repeated on the real Render staging instance in T130.

**Framework limitation (Next 16.4)**: `notFound()` thrown by a page under `[locale]` (the catch-all
`[...rest]` page and any product or category page) answers with status 404, but the initial HTML is
Next's empty `__next_error__` shell and the not-found UI is rendered in the browser. Reproduced in a
bare Next app without our proxy, plugin or layouts; URLs that match no route at all are rendered on
the server. This is accepted, so E2E checks the 404 content after the page has loaded.

## R8. Image storage and delivery

**Decision**: **Cloudflare R2** (S3-compatible, EU jurisdiction buckets), accessed with
**@aws-sdk/client-s3**:
- `ac-images-private`: every processed variant (drafts included) and order snapshot thumbnails.
  Admin screens load them through an authenticated same-origin route
  (`/api/admin/media/...`, `Cache-Control: private, no-store`), so no presigned URLs or extra CSP
  origins are needed and private images are never reachable without a full admin session.
- `ac-images-public`: copies of the variants of products that are currently *published*
  (available or not-available-to-order), served from `https://img.<shop-domain>` through
  Cloudflare's CDN with `Content-Type: image/webp`, `X-Content-Type-Options: nosniff` and
  `Cache-Control: public, max-age=86400` (not immutable, so unpublished photos leave CDN caches
  within a day). `Content-Type` and `Cache-Control` are stored per object at upload; R2 does not add
  `X-Content-Type-Options` by itself, so a Cloudflare **Response Header Transform Rule** on
  `img.<shop-domain>` sets `X-Content-Type-Options: nosniff` (free plan feature), verified on
  staging with `curl -sI` (launch checklist). Keys contain a random id, so a variant URL is not guessable. Publishing copies
  variants in; hiding, drafting or deleting removes them. Storage serves static bytes only and
  cannot execute code.
- `ac-backups`: encrypted database dumps and a daily copy of the private images bucket (R13).
- At order confirmation the main photo's 400 px variant is copied to `orders/<order-id>/...` in
  the private bucket, so past orders keep their photo after the product is deleted (US1 #5).
- Individually removed photos are purged from storage 30 days after removal (protects against
  mistakes); deleting a whole product (after a confirmation dialog) deletes its photo files
  immediately, while order snapshots keep their own copies.
- Local development and tests use a filesystem driver behind the same `Storage` interface.
- EU-jurisdiction buckets are reached only through the jurisdiction endpoint
  `https://<account>.eu.r2.cloudflarestorage.com` (env `R2_JURISDICTION=eu`, the default), used by
  the app and by the backup job's rclone config; the default endpoint would not find them.

**Rationale**: R2 has no egress fees and a free tier (10 GB storage, 1M writes, 10M reads per
month) far above this shop's needs; separating public and private buckets means draft photos
are never publicly reachable (SC-007), and image traffic does not consume Render bandwidth.

**Alternatives considered**: *Serve images through the app* (uses Render bandwidth and CPU,
5 GB/month included); *one public bucket with unguessable keys for drafts* (drafts would be
publicly reachable by URL — rejected for SC-007); *Render persistent disk* (no CDN, ties images
to one instance, separate backups).

## R9. Transactional email

**Decision**: **Resend**, free plan (3,000 emails/month, 100/day), sending domain verified with
SPF, DKIM and DMARC, **EU region** (Ireland). Emails are rendered by the app as simple HTML +
plain-text from translated templates (`src/server/email/templates/`), with `dir="rtl"` for
Hebrew. All emails go through an **outbox table**: written in the same transaction as the
business change, sent right after commit, retried by the job loop every minute with backoff
(SC-003), and recorded as sent exactly once.

**Rationale**: Expected volume (a few hundred orders/month × ≈3 emails ≈ ≤ 1,000/month) fits the
free plan; simple HTTP API; EU data region. Contact-form messages exist only in the outbox until
sent: the visitor's address is kept in the row's `reply_to` column (used as the `Reply-To` header)
and erased together with the body after sending (data minimisation). A row that ends `failed`
keeps its body and `reply_to` until the row is deleted 30 days later, so the owner can still see
what was not delivered.

**Alternatives considered**: *Brevo* (EU company, 300/day free; heavier marketing-oriented
product; a fine fallback); *Amazon SES* (cheapest at scale, more setup: sandbox exit, IAM);
*Postmark* ($15/month, over need); *Gmail SMTP* (deliverability and account-security risk).
React Email was skipped: a few templates do not justify the dependency.

## R10. Visitor statistics (cookieless)

**Decision**: **Built-in, first-party, aggregate-only counter.** A tiny script (bundled, same
origin) sends `navigator.sendBeacon('/api/v', {path, referrerHost})` on every page view — the first
load and every client-side navigation (`usePathname()` change), because the shared layout does not
re-render — with `referrerHost` only on the first beacon of a document load (later beacons carry no
referrer and count as page views, not visits). The server
drops obvious bots (user-agent list), keeps **no IP, no user-agent, no identifier**, and
increments daily aggregate rows: page views per path per day, and *visits* (page views whose
referrer is empty or another site) per referrer host per day. The admin statistics page shows
visits over time, most-viewed products and top referring sites (FR-037). Nothing is stored on
the visitor's device.

**Rationale**: Satisfies FR-037/FR-037a with zero cost, zero third parties (nothing to list in
the Privacy Policy, no CSP exception, no consent question), and about one table, one endpoint
and one admin page.

**Alternatives considered**: *Plausible Cloud* ($9/month ≈ ₪33 — a third of the budget);
*Umami Cloud free tier* (good, but a third-party processor receiving visitor IPs and a script
host to allow in CSP); *Cloudflare Web Analytics* (free, but third-party beacon and US
processing). Any of these could replace the built-in counter later without changing the
consent design.

## R11. Bot and abuse protection

**Decision**: Layered, invisible to people: (1) a hidden honeypot field, (2) a signed
form-render timestamp that rejects submissions faster than 3 seconds or older than 2 hours,
(3) per-IP rate limits (IP stored only as a keyed HMAC, rotated daily) for checkout (10 per 10
minutes), contact (5 per hour), Google sign-in start (10 per 15 minutes) and the analytics
beacon (60 per minute), kept in a Postgres table, and (4) server-side validation. Escalation
path if abuse appears: add **ALTCHA** (self-hosted proof-of-work, no third party, no cookies).

**Rationale**: FR-036 and constitution IV "abuse protection … privacy-friendly"; no third-party
CAPTCHA (no cookies, no data sent to Google/Cloudflare).

**Alternatives considered**: *Cloudflare Turnstile* (free and mostly invisible, but a
third-party script that processes visitor signals); *reCAPTCHA* (tracking concerns, puzzles).

## R12. Background work

**Decision**: An **in-process job loop** started from Next.js `instrumentation.ts` (Node runtime)
on the single web instance: every 60 s it sends due outbox emails; every 5 minutes it runs the
payment recovery sweep and deletes pending checkouts older than 48 h (so none outlives the
personal-data register's 48 h by more than minutes); once a day it runs maintenance (7-year order
anonymisation FR-040, purge of old rate-limit rows, consent and activity-log retention, 30-day image purge). Each job
takes a lease on its `job_run` row and records its last run there, so overlapping instances
during a deploy cannot double-run. The guard is a **lease** (`locked_until`) on the `job_run` row,
not a session-level advisory lock (which leaks on a connection pool); outbox rows are claimed by
moving them to `sending` with a `locked_until` in one short transaction and sent outside it. The nightly backup is a separate Render Cron Job (R13)
because it needs `pg_dump`.

**Rationale**: No queue service, no extra paid service; safe under deploy overlap.

**Alternatives considered**: *Render Cron Jobs for everything* (each run starts a container; a
1-minute outbox cadence would cost more and add latency); *external queue (e.g., Upstash)*
(another vendor for no benefit at this scale).

## R13. Backups and restore

**Decision**: Two layers. (1) Render managed Postgres point-in-time recovery (3 days on
Hobby). (2) A nightly Render Cron Job (`ops/backup/`, Alpine image with `postgresql17-client`,
`age`, `rclone`) runs `pg_dump --format=custom`, encrypts it with **age** to a public key whose
private key is kept offline by the maintainer (the server cannot decrypt its own backups),
uploads it to `ac-backups/db/daily/` every night and, on the 1st of each month, also to
`ac-backups/db/monthly/` (R2 lifecycle rules per prefix: daily objects expire after 30 days,
monthly after 365 days — lifecycle rules work by age per prefix, so one prefix could not keep both),
and runs
`rclone copy` (no deletes) from the private images bucket into `ac-backups/images/`. A restore
into a scratch database is performed and documented before launch (constitution IV).

**Rationale**: Off-platform, encrypted copies survive a Render account problem; cost ≈ $1/month.

## R14. Content Security Policy and headers

**Decision**: Per-request **nonce-based CSP** set in `src/proxy.ts` (Next.js 16's name for middleware):
`default-src 'self'; script-src 'self' 'nonce-…' 'strict-dynamic'; style-src 'self' 'nonce-…';
img-src 'self' https://img.<domain> data: blob:; font-src 'self'; connect-src 'self';
frame-src 'none'; frame-ancestors 'none'; base-uri 'none'; object-src 'none';
form-action 'self' https://<payplus-payment-host>; upgrade-insecure-requests`, plus HSTS
(2 years, includeSubDomains, preload after launch), `X-Content-Type-Options: nosniff`,
`Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` denying camera,
microphone, geolocation, payment etc., `Cross-Origin-Opener-Policy: same-origin`. Pages render
dynamically (nonce per request) and read Postgres directly with no data cache — queries take
milliseconds at this scale, and admin changes (hide, price) show on the very next request. Fonts are self-hosted by `next/font` at build time (no runtime
request to Google). Inline `style` attributes are not allowed by this CSP, so components use
classes, `<progress>`/`<meter>` or SVG attributes for dynamic sizes. The proxy's matcher excludes
the image-upload route so its 20 MB bodies are not cut by the proxy body-buffering limit;
`Cache-Control: no-store` and `X-Robots-Tag: noindex` for admin, auth, checkout and order pages
(and `no-store` for `/api/payments/status`) are set in `next.config.ts` `headers()`. The static
security headers (HSTS, nosniff, Referrer-Policy, Permissions-Policy, COOP) are also set there for
every path, because the proxy matcher skips static files, `sitemap.xml`, `robots.txt` and the
upload route; the proxy adds the per-request CSP and nonce.

**Per-path and per-environment additions**: on `/admin/sign-in`, `/admin/sign-in/*` and
`/admin/setup`, `form-action` also lists the origin of the OIDC issuer (`OIDC_ISSUER`:
`https://accounts.google.com` in production, the mock `http://localhost:4011` in development and
tests). The Google button is a form POST to `/api/auth/google/start`, which answers `303` to the
issuer's authorisation endpoint, and Chromium enforces `form-action` on redirects that follow a form
submission. `google.ts` checks at discovery that the authorisation endpoint has the issuer's origin.
In development only (`NODE_ENV=development`) `script-src` adds `'unsafe-eval'`, which React's
development build needs; production and test builds never have it.

**Cross-site admin links**: a top-level `GET` of an admin page with `Sec-Fetch-Site: cross-site`
(e.g. the order link in a `new-order` email opened in webmail) arrives without the `SameSite=Strict`
admin cookie. The proxy answers it with the same minimal same-site re-navigation page the Google
callback uses, so the next request carries the cookie; it reads no session and grants nothing.

**Note on auth**: the proxy only sets headers and locale (plus the bounce above); **authorisation is never done in
the proxy/middleware** (CVE-2025-29927 showed middleware can be bypassed). Every admin page, Server Action
and route handler calls `requireAdmin()` in the data-access layer.

## R15. Testing and quality tooling

**Decision**: **Vitest** (unit + integration on PGlite), **Playwright** (E2E on Chromium with the
CDP virtual WebAuthn authenticator for passkeys, a local mock OIDC issuer —
**oauth2-mock-server** — standing in for Google, the `fake` payment adapter with signed
callbacks, and mobile viewport projects), **@axe-core/playwright** for WCAG 2.1 AA checks in
both directions, **ESLint** (with `eslint-plugin-i18next` no-literal-string on UI code) and
**TypeScript strict**. Dependency gate: `pnpm audit --audit-level=high` in CI and in the local
`pnpm verify` script; Renovate (or Dependabot) for updates; exact pins + lockfile. Pre-launch
dynamic scan: **OWASP ZAP baseline** against the staging site.

**Rationale**: Covers every constitution VI critical path in automated tests without external
accounts or Docker for the unit/integration layer.

## R16. Rich text for editable pages

**Decision**: Owner edits About/legal pages as a constrained **Markdown** subset in a textarea
with toolbar buttons (heading, bold, list, link) and a live preview; rendered server-side with
**markdown-it** with HTML disabled (raw HTML is escaped) and links limited to `https:`,
`mailto:` and `tel:`.

**Rationale**: Safe by construction (no HTML injection), tiny dependency, toolbar hides syntax
from the owner. A WYSIWYG editor (TipTap/Lexical) would add hundreds of KB and an HTML
sanitiser for little benefit on a handful of pages.

## R17. Client IP handling

**Decision**: Client IP is read from the proxy header chain with a configured number of trusted
hops (`TRUSTED_PROXY_HOPS`, 1 for Render alone, 2 when Cloudflare proxying is enabled), used
only to compute a daily-rotating keyed HMAC for rate limiting, and never logged or stored raw.

## R18. Interpretations of the spec (recorded, not new product decisions)

- **USD and enabling an international zone (FR-015 + edge case)**: following FR-015 literally,
  an international zone cannot be enabled while any published product (or non-zero option
  adjustment) lacks a USD price; the settings screen lists the products to fix. Once a USD zone
  is enabled, a published product cannot be saved without a USD price. The edge-case flag
  ("items without a USD price are unavailable for that destination") remains as a safety net
  for stale carts.
- **Adding zones (FR-024 "owner or maintainer")**: the owner edits existing zones (fees,
  threshold, enable/disable) in the admin area; adding a new zone is a maintainer CLI command
  (`pnpm zone:add`). The checkout flow is zone-driven, so no code changes are needed.
- **"Delete" of customer data (FR-039)**: because every order is within the 7-year tax period
  until it is anonymised, "delete" anonymises that customer's orders and deletes any non-order
  data (pending checkouts and all their outbox rows, sent or not, matched by recipient, by
  `reply_to` for contact messages, or by `order_id` for owner notifications about their orders,
  which carry their details in failed bodies). Amounts, items, dates and country remain.
- **Order confirmation page**: reachable only through an unguessable link for 30 days (offline
  orders: random token; online orders: `HMAC(secret, 'order:' + hex(resume_token_hash))`, computable from the stored hash
  by the callback/sweep and from the link token by the return page); it shows
  order number, items, totals, payment instructions and preparation time, never the address or
  phone.
- **Admin sessions**: "a period of inactivity" = 30 minutes; absolute 12 hours.
- **Very large photos (edge case)**: "accepted and reduced automatically" is implemented for every
  normal phone photo — up to 20 MB and 51,000,000 pixels, so phones' 50 MP modes (e.g. 8160×6144 ≈ 50.1 MP) fit (phones'
  standard modes are 12–50 MP, a few MB to
  ~15 MB). Larger files (e.g., 200 MP "high-resolution mode" shots) are rejected with a message
  asking for a normal-mode photo, because decoding them would exceed the 512 MB server.
  **Confirmed by the user (2026-11-07)** and written into the spec's edge cases.
- **Sort by price (FR-009)**: the price sorts order products by their ₪ base price
  (`price_ils_minor`, ties by newest). A card may show a lower "from" price when an option
  subtracts from the base; that rare case is accepted to keep the query simple.
- **Order status shortcut (FR-028)**: the owner may move a `new` order straight to `shipped` /
  `ready_for_pickup` without passing through "in preparation" (made-to-order pieces are often ready by
  the time she opens the order screen); the customer email is the same.
- **Postal code (FR-013, FR-025)**: optional at checkout (many customers do not know theirs and
  couriers do not require it); when given for Israel it must be 7 digits.
- **Customer data export format ("readable file")**: a pretty-printed UTF-8 JSON file with
  clearly named fields.

## R19. Legal and privacy compliance approach (constitution VII)

- **Israeli Privacy Protection Law (Amendment 13, in force since 2025-08-14) and Data Security
  Regulations**: the customer database is a small business database with ≤ 3 authorised users
  and no information of special sensitivity (card data never touches the shop), so the *basic*
  security level applies. The project supplies drafts of the database-definition document,
  the security procedure, the access-authorisation list, a severe-incident (breach) response
  procedure and a yearly review checklist (`docs/privacy/`). A collection notice (purpose,
  whether providing data is a legal obligation, recipients) is shown at checkout next to the
  submit button, linking to the Privacy Policy.
- **Consumer Protection Law (distance selling, section 14C) and Cancellation Regulations**:
  checkout shows seller identity, full price including delivery, delivery terms and
  each item's preparation time (in the checkout order summary) before the order; the confirmation email contains the written disclosure
  details and the cancellation policy. Draft cancellation policy notes the statutory exception
  for goods made specially for the consumer and the cancellation-fee cap, for the legal
  reviewer to confirm. The contact form serves as an online channel for cancellation notices.
- **Communications Law (anti-spam, section 30A)**: separate unticked marketing checkbox; consent
  and date stored on the order; no marketing sending in scope.
- **GDPR-readiness**: EU hosting, data minimisation per field (data-model), export/correct/
  anonymise tools, retention automation, processor list, consent mechanism ready.
- **Seller details (user, 2026-11-07)**: the business is VAT-registered (עוסק מורשה), so ₪ prices
  include VAT and the registration number is the ע.מ. number; the business address (שדרות בן-צבי
  120/18) is published in the footer, Terms and order confirmation email (FR-047 updated). Tax
  invoices stay outside the shop (spec assumption).
- **Admin Google 2-Step Verification (user, 2026-11-07)**: accepted as a launch-checklist step and
  a documented residual risk, since the shop cannot verify it.
- **Synced Android passkeys (user, 2026-11-08)**: accepted residual risk (R6), stated in the threat
  model.
- **Database role (user, 2026-11-08)**: the app, migrations and backups use the single Render-provided
  database account (allowed by constitution IV 1.3.0).
- **Code hosting (user, 2026-11-07)**: GitHub (Actions CI, Renovate, Render deploys from GitHub).
- **Processors to list in the Privacy Policy**: Render (hosting, database; EU), Cloudflare (DNS,
  image storage/CDN — sees visitors' IP addresses when images load from `img.` — and client-side
  encrypted backups; EU jurisdiction buckets; at launch the shop domain is DNS-only, not proxied, user
  decision 2026-11-08, but Render may itself route traffic through Cloudflare: check Render's
  sub-processor list before writing the Privacy Policy — proxying it later puts all shop traffic incl. checkout forms through
  Cloudflare and needs this list and the Privacy Policy updated first), PayPlus (payments; Israel), Resend (email; EU
  region). Google receives data only about admins (sign-in), not customers.
