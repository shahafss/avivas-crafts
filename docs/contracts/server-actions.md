# Contract: Server Actions

> **Living document.** Moved from `specs/001-online-crafts-shop/` on 2026-11-09. Every feature that
> changes this contract updates this file in its own branch. Unqualified references to `spec.md`,
> `plan.md`, `research.md` (R-numbers), `quickstart.md`, FR-/SC- numbers and task IDs mean the
> ones in [`specs/001-online-crafts-shop/`](../../specs/001-online-crafts-shop/) unless a later
> spec is named.

Server Actions are the write interface for forms. Each action:

1. for admin actions, calls `requireAdmin()` **before anything else, including input parsing**
   (returns the admin or throws → redirect to sign-in), so an unauthenticated call with missing or
   malformed input still gets the sign-in redirect and no admin action is reachable without a
   `full` session;
2. validates input with a Zod schema (shared with the client for instant feedback, but the
   server result is authoritative);
3. returns `ActionResult<T> = { ok: true, data: T } | { ok: false, fieldErrors?: Record<string, MessageKey>, formError?: MessageKey }`
   where `MessageKey` is a translation key, rendered next to the field in the visitor's language
   (FR-014);
4. writes an `admin_activity` row for every admin change (FR-035);
5. does not invalidate any cache: pages render dynamically from Postgres, so changes are visible
   on the next request.

Next.js checks the `Origin` header of every Server Action against the host (CSRF defence); the
allowed origins list is the shop domain only.

## Storefront actions (`src/app/[locale]/(shop)/**/actions.ts`)

### `priceCart(input)`

- **Input**: `{ items: {productId, optionValueIds[], quantity}[] (≤ 50), zoneCode?: string }`
- **Output**: `{ currency, lines: {key, productId, slug, name, imageUrl, options: {group, value}[], prepTime, unitPriceMinor, quantity, lineTotalMinor, flag?: "unavailable"|"not_orderable"|"choose_options_again"|"no_usd_price"}[], subtotalMinor }`
- Read-only; names and `prepTime` (the product's preparation time) in the request's locale with
  Hebrew fallback. The checkout order summary shows `prepTime` per line before the order is placed
  (distance-selling disclosure, research.md › R19).

### `quoteCheckout(input)`

- **Input**: cart items + `{ deliveryMethod: "shipping"|"pickup", country?: string }`
- **Output**: `{ zoneCode, currency, subtotalMinor, deliveryFeeMinor, totalMinor, flags[], shippingAllowed: boolean, pickupAllowed: boolean, lines[] }` (`lines` = the priced lines of `priceCart`, so the checkout summary needs one round trip; input also takes `locale`)
- Unsupported country, including the UI-only "Other country" value `other` → `{ok:false, formError:"checkout.ships_israel_only"}` (edge case).
- Free shipping when `subtotalMinor >= free_shipping_threshold_minor` (FR-023).

### `placeOrder(input)`

- **Input**:
  ```text
  items[]; fullName; phone; email; deliveryMethod; address?{country, city, line1, line2?, postalCode};
  paymentMethod: "online"|"offline"; acceptTerms: true; marketingOptIn: boolean (default false);
  note?; honeypot (must be empty); formToken (signed render timestamp); locale
  ```
- **Checks**: in `APP_ENV=production`, refused with `checkout.shop_not_ready` while any seed placeholder
  remains in the business details or notification emails (the seeded working shop name is not a
  placeholder; `placeholderFields()`,
  src/server/settings/settings.ts; the admin dashboard lists them); rate limit (10 / 10 min per
  IP-hash), honeypot, form token age 3 s–2 h, payment and
  delivery methods enabled, all lines orderable (re-priced server-side, any flag → error listing
  the lines), terms accepted.
- **Offline** → creates `order` (status `new`, payment `awaiting_payment`, number assigned),
  enqueues customer confirmation (with payment instructions) and owner notification, returns
  `{ redirect: "/{locale}/order/{token}" }`.
- **Online** → creates `pending_checkout`, calls `provider.createPaymentPage()`, returns
  `{ redirect: <provider URL> }`. No order, no emails yet.
- Prices are frozen into the order / pending checkout at this moment (FR-016).

### `retryOnlinePayment({resumeToken})` / `switchToOfflinePayment({resumeToken})`

From the payment-return page after failure (US2 #5). Both take `{resumeToken, acceptNewTotal?: boolean}`,
lock the pending row (`SELECT … FOR UPDATE`), refuse with `{ok:false, formError:"checkout.already_completed"}`
and change nothing unless its state is `awaiting_provider` or `failed` (a `confirmed`, `switched_offline`
or `mismatch` row — whose personal columns may already be cleared — never gets a new payment page or a
second offline order, e.g. after the browser's back button or a double submit), and **re-price the
stored lines first**, with the same
rule: if the new total differs from `pending_checkout.total_minor` and `acceptNewTotal` is not
`true`, they change nothing and return `{ok:false, formError:"checkout.total_changed", data:{newTotalMinor, currency}}`;
the page shows the new total and calls again with `acceptNewTotal: true`. Any flagged line →
`{ok:false, formError:"checkout.lines_unavailable"}` with a link back to the cart.

- **Retry** (if not expired): disables the old page; if the total changed (and was accepted),
  updates the row's `lines` and totals; creates a new provider page for the current total; sets
  `state = awaiting_provider`, `provider_page_id`, `last_status_check_at = null`. The pending row's
  totals change only after the visitor's acceptance. (A late payment of the disabled old page at
  the old amount would then be reported to the owner as a mismatch; disabling first makes this a
  narrow race.)
- **Switch**: refuses with `checkout.offline_unavailable` when offline
  payment is disabled in settings (the return page then hides "pay directly instead"); disables the provider page; creates an offline order from
  the stored details at the (accepted) current prices through the same code path as an offline
  `placeOrder` (`order_event created`, `order-confirmation` and `new-order` emails, `terms_accepted_at` /
  versions / `marketing_opt_in_at` copied from the pending checkout, line snapshots incl. images); sets the row to `switched_offline`, stores the new order's id in `order_id` and clears
  its personal columns. Returns `{ok:true, redirect:"/{locale}/order/{token}"}` exactly like an offline
  `placeOrder` (the new order's random token), so the visitor lands on the order page with the payment
  instructions (US2 #6).

### `submitContact(input)`

- **Input**: `{ name (2–100), email, message (10–5,000), honeypot, formToken, locale }`
- Rate limit 5 / hour per IP-hash. Enqueues `contact-message` email to the notification
  addresses with `replyTo` = visitor email (stored in `email_outbox.reply_to`, erased on send).
  Returns `{ ok: true }`.

### `saveConsent(input)` (only when an optional category is enabled)

- **Input**: `{ choices: Record<category, boolean> }`
- Creates a `consent_record`, sets `ac_consent` cookie (id + choices + version), returns
  `{ ok: true }`. Rejecting everything is the same one-click action as accepting everything.

### `setLocale(locale)` is not an action: the language switch is a plain link to

`/api/locale?to=<locale>&path=<same page in that locale>`, which is the only place `NEXT_LOCALE`
is written (see http-endpoints.md).

There are no restricted sessions: every `full` session has the same permissions (FR-034). A passkey
added through a recovery code cannot produce a `full` session until another admin approves it
(research.md › R6).

**⟳ Passkey re-check** (FR-032, ASVS 5.0 V7.5): actions marked ⟳, and adding a passkey on this
device (`/api/auth/passkey/register/*` purpose (a)), call `requireRecentAuth()` instead of
`requireAdmin()`: it first does everything `requireAdmin()` does (so the signed-out redirect still
comes first), then refuses with `{ok:false, formError:"admin.reauth_required"}` (route handlers:
`403 {"error":"reauth_required"}`) unless the session's `reauth_at` is less than 5 minutes old. The
screen then runs the passkey re-check (`/api/auth/reauth/*`, http-endpoints.md) and repeats the
action. No other admin action asks for it — in particular not `revokeSession`, `signOutEverywhere` or
`POST /api/auth/sign-out`.

**Admin pages and loaders**: every `src/app/admin/(protected)/**/page.tsx` calls `requireAdmin()`
itself before loading data; the protected layout's call is not enough, because Next.js does not
re-render the layout on client-side navigation.

All destructive admin actions (`deleteProduct`, `deleteOptionGroup`, cancel order, `markOrderRefunded`,
`anonymizeCustomer`, `removeAdmin`, `removePasskey`, `deleteCategory`) require a confirmation
dialog in the UI and `confirm: true` on the server (constitution II).
